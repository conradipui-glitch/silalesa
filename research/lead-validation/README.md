# Проверка реальных обращений и готовности услуг к продвижению

**Статус: техническая подготовка, не отчёт о результатах продаж.** Дата: 8 октября 2026. Ни в этом файле, ни в репозитории нет подтверждённых журналов входящих обращений, смет, заказов или занятости бригад.

## Что действительно измеряем

Данные поискового спроса из [yaai](../yaai/omsk-pain-discovery-2026-10-08.md) помогают выбрать вопросы и направление. Но просмотры страницы, поисковые показы и даже клик по WhatsApp — **не факт получения заявки**.

| Этап | Когда засчитывать | Источник проверки |
|---|---|---|
| Переход | Посетитель открыл прямую ссылку с UTM | Яндекс.Метрика **после подключения подтверждённого счётчика** |
| Контактное намерение | Клик по WhatsApp или телефону (событие `lead_intent`) | Только счетчик/журнал событий сайта; **не подтверждает отправку** |
| Полученная заявка | Сообщение реально поступило в WhatsApp/по телефону | Сотрудник вручную пометил реальный контакт |
| Квалифицирована | Заказчик обозначил вид работ, объект и возможность выполнения согласованного объёма | Сотрудник подтверждает по карточке обращения |
| Смета | Отправлено конкретное коммерческое предложение | Сотрудник подтверждает по факту отправки |
| Договор | Реально согласован заказ | Сотрудник подтверждает по документам, не из аналитики кликов |

**Минимальный реестр:** одна запись на один уникальный контакт с внутренним обезличенным ID, датой, услугой, источником (например, `telegram`, `vk`, `unattributed`), кампанией и текущим статусом. Не заносить в публичный GitHub телефоны, переписку, адреса объектов, персональные данные, договоры и цены клиента. Использовать CRM или приватный рабочий файл, доступный только уполномоченным.

Если данные недоступны, писать `нет данных`, а не ноль. Не рассчитывать процент конверсии без корректного числа посещений по каждой кампании. Не сравнивать «квалифицированные заявки» с частотностью Wordstat — это разные величины.

## Запуск трёх тематических публикаций

Ссылки ниже **готовы** для карточек в Telegram/ВКонтакте. Они открывают компактную страницу с индивидуальной услугой, полями объекта и подготавливают сообщение в WhatsApp только после нажатия:

- Кровля: `https://conradipui-glitch.github.io/silalesa/brief/roofing/?utm_source=telegram&utm_medium=post&utm_campaign=roof_oct26`
- Стяжка: `https://conradipui-glitch.github.io/silalesa/brief/screed/?utm_source=vk&utm_medium=post&utm_campaign=screed_oct26`
- Фасады: `https://conradipui-glitch.github.io/silalesa/brief/facades/?utm_source=telegram&utm_medium=post&utm_campaign=facade_oct26`

Каналы допустимы только из ограниченного списка. `utm_campaign` принимает латинские символы, цифры, `_` и `-` длиной до 48 символов. Непроверенные метки отбрасываются. Метка публикации видна в предпросмотре WhatsApp-сообщения и может быть сохранена сотрудником **после реального поступления обращения**. Метка показывает выбранный ярлык ссылки, а не гарантированно достоверный путь клиента.

При смене услуги метка сохраняется. Личную переписку, адрес объекта, введённую площадь, описание работ или телефон аналитика `track` не получает.

## Что пока не подключено

В `.github/workflows/pages.yml` сборка запускается без `VITE_YM_COUNTER_ID` и без скрипта инициализации `ym`. Следовательно, в текущем проекте нет подтверждения, что события `lead_intent` реально попадают в **Яндекс.Метрику**; локальный буфер событий — только средство технической отладки. Секреты API из `yaai` — **не** идентификатор действующего счётчика Метрики.

Подключать действующий счётчик и цели только после подтверждения владельцем ID, прав доступа, политики конфиденциальности, согласий и требований 152-ФЗ. Предложение по целям: `lead_intent` как клик, плюс отдельный **внешне подтверждённый** этап `qualified_lead` или офлайн-конверсия, когда в CRM появился реальный контакт.

Сайт не отправляет заявки на сервер и не может знать, отправил ли человек сообщение в другом приложении.

## Проверка возможности выполнить услуги

Из устного перечня работ и контента сайта известно, какие направления **предлагаются**. Но это не доказательство доступности бригады, конкретного метода, лицензии, гарантий, цены или выполненного объекта.

| Направление | Подтверждено содержимым сайта | Ещё нужно подтвердить у исполнителя |
|---|---|---|
| Кровля | Монтаж/ремонт кровли указан в перечне услуг | Типы кровель и высота объектов, доступность на сезон, материалы/состав, фото собственных работ, условия гарантии |
| Полусухая стяжка | Отдельная коммерческая страница и заявленный стартовый ориентир `от 600 ₽/м²` | Актуальность цены, минимальный объём, высота подачи, состав работ, техника, собственные фотографии и допустимые типы объектов |
| Фасады | Подготовка, утепление, наружная отделка упомянуты на сайте | Какие фасадные системы действительно выполняются, высотность, материалы, собственные объекты, сезонность и сроки |

До подтверждения **не** добавлять на сайт реальные/условные кейсы под видом портфолио, вымышленные фотографии объектов, конкретные гарантийные сроки, цены за м², бригады или «свободные места».

## Правило приоритета

После 2–4 недель размеченных обращений (достаточность данных оценить отдельно по факту) сопоставляем по каждому каналу и направлению: сеансы → контактные клики → **реальные полученные** обращения → квалифицированные → сметы → договоры. Сопоставляем также потенциальную маржинальность и доступность исполнителей, подтверждённую владельцем.

Результат: решение о приоритете и отдельной SEO-странице для кровли/фасадов, уточнение контентных блоков для стяжки и только затем дальнейшая SEO-итерация. Отсутствие данных оставляет решение открытым.
