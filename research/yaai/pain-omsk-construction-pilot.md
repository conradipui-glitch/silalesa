# Сила Леса × yaai Pain Discovery — пилот под строительные работы

Актуальная версия движка: [yaai #24](https://github.com/conradipui-glitch/yaai/pull/24) и [yaai #25](https://github.com/conradipui-glitch/yaai/pull/25). Использовать [SKILL.md](https://github.com/conradipui-glitch/yaai/blob/main/.agents/skills/pain-discovery/SKILL.md). Этот пилот не обновляет сайт и не делает платные вызовы автоматически.

## Цель

Проверить, **с какими конкретными вопросами и сложностями люди ищут кровлю, полусухую стяжку, фасады в Омске и области**. Не приписывать жителям региона вымышленные черты характера. Сопоставлять:

1. проверенную помесячную динамику фраз 2024–2025: [первый отчёт](../../yaai-wordstat-omsk-2024-2025-report.md);
2. текущие уточнения Wordstat TopRequests (включая связанные формулировки, но без сложения пересекающихся частотностей);
3. фрагменты текущей региональной выдачи Яндекса и URL;
4. классификацию Jev: предполагаемая боль, вопрос, поиск решения, неопределённость, голос источника;
5. ручную проверку доказательств, где Jev помечает «review».

Конфигурация направлений и лимитов — [pain-omsk-construction-pilot.json](./pain-omsk-construction-pilot.json). Регион **Омская область**, кандидат кода — `11318`; подтвердить через `getRegionsTree` до реального платного исследования, не подменять кодом города Омск `66`.

## Порядок исследования

Рабочая папка для результатов должна оставаться в workspace проекта (или приватном исследовательском артефакте), не в репозитории движка `yaai`. Секреты уже настроены в `yaai` GitHub Actions, не переносить их в GitHub «Силы Леса», не показывать в переписке.

Для одного направления после ручного подтверждения региона и лимита:

```bash
# Запуск из checkout yaai; переменные окружения с ключами подаются в доверенной среде
npm run pain:wordstat -- \
  --seeds "кровельные работы,ремонт кровли" --region 11318 \
  --num-phrases 35 --out /private/omsk-roofing-wordstat.json --execute

npm run pain:prepare -- \
  --topic "кровельные работы" --wordstat /private/omsk-roofing-wordstat.json \
  --limit 4 --out /private/omsk-roofing-plan.json \
  --query-file /private/omsk-roofing-queries.txt

# Проверить запросы в файле на соответствие бизнесу ДО запуска SERP
npm run serp:collect -- \
  --query-file /private/omsk-roofing-queries.txt --region 11318 \
  --groups 5 --out /private/omsk-roofing-serp.json --execute

npm run pain:analyze -- \
  --topic "кровельные работы" \
  --wordstat /private/omsk-roofing-wordstat.json \
  --serp /private/omsk-roofing-serp.json \
  --limit 10 --out /private/omsk-roofing-pain-map.json \
  --md /private/omsk-roofing-pain-map.md \
  --evaluation-out /private/omsk-roofing-jev-evidence.json --execute
```

Аналогично со своими seeds выполнить `screed` и `facades`. Пилотные лимиты на **каждое направление**: 2 Wordstat, до 4 SERP-запросов × 5 результатов, до 10 решений Jev. Это не оценка фактической стоимости: проверить тариф и фактически записанный расход, прежде чем расширять.

## Как применять выводы

Каждая редакторская рекомендация должна содержать: название услуги, подтверждённую поисковую фразу и отдельно её частотность (если есть), ссылку/дату/фрагмент SERP, Jev-гипотезу, статус ручной проверки, страницу сайта и предлагаемый тест.

- `roofing`: проверить, нужна ли отдельная коммерческая SEO-страница и какие вопросы поставить возле CTA. Микространица `/brief/roofing/` уже опубликована.
- `screed`: усиливать действующую страницу `/polusuhaya-styazhka-omsk/`; избегать дублей. Социальная ссылка `/brief/screed/`.
- `facades`: проверить существующий оффер, коммерческий SERP и целесообразность полноценной SEO-страницы. Социальная ссылка `/brief/facades/`.

Переход от гипотез к сайту: **Wordstat и SERP → Jev Pain Map → выбор проверенных FAQ/аргументов → редакторская проверка фактов → PR → Playwright → эксперимент с UTM и обращениями**.

Не представлять фрагменты выдачи или запросы Wordstat как прямые отзывы омичей, Jev certainty — как достоверность, а частотность — как количество клиентов. Без реальных кейсов и подтверждённых условий не обещать сметы, гарантии или сроки.
